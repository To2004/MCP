# Methodology audit (independent LLM judge)

Each claim was verified in isolation by the local LLM, shown only the relevant source. Verdicts: ✅ pass · ⚠️ concern · ❌ fail · ❓ no answer.

## ✅ no_data_leakage — pass (severity: none)

*Claim:* The scanner never reads the design-time ground-truth tables (reports/samples/* or reports/evaluation/*); they only grade it.

*Reasoning:* The provided code does not show any paths where the scanner reads from 'reports/samples/*' or 'reports/evaluation/*'. The scanner only reads tool lists from 'reports/tool_lists/<kind>.json', which is explicitly stated to be a saved response from the server's own advertised tool list, and it never accesses ground-truth tables.

*Evidence:* src/mcp_security/scanner/scan.py, src/mcp_security/static_scoring/pipeline.py

## ✅ tools_from_server_tools_list — pass (severity: none)

*Claim:* The scanner's tools come from the server's own saved tools/list (reports/tool_lists/<kind>.json), not a hand-authored catalog, and carry no pre-assigned risk label.

*Reasoning:* The code in `load_tool_list` function reads the server's own saved tools from `reports/tool_lists/<kind>.json`, which is generated by running `scripts/save_tool_lists.py`. The `_spec_from_entry` function creates a `ToolSpec` object without assigning any pre-assigned risk label, only using data provided by the server.

*Evidence:* src/mcp_security/scanner/tool_list.py: load_tool_list, tool_list_path, _spec_from_entry

## ✅ llm_only_no_fabrication — pass (severity: none)

*Claim:* The scanner runs the scorer in strict mode (scan_server calls build_static_table with strict=use_llm), and in strict mode every primitive — domain, tool_impact, sensitivity, blast_radius, band, baseline — routes a missing model answer through _strict_fail, which raises LLMUnavailableError instead of substituting a heuristic.

*Reasoning:* The code in `StaticScorer` class ensures that when `strict=True`, any missing model answer results in a call to `_strict_fail`, which raises `LLMUnavailableError`. This is evident from the implementation of methods like `score_tools`, `score_assets`, `score_blast`, and `score_bands`. The `scan_server` function in `src/mcp_security/scanner/scan.py` also correctly sets `strict=use_llm`, ensuring strict mode when required.

*Evidence:* src/mcp_security/static_scoring/pipeline.py: _strict_fail method, score_tools, score_assets, score_blast, score_bands methods; src/mcp_security/scanner/scan.py: scan_server function

## ✅ scoring_uses_scan_not_tables — pass (severity: none)

*Claim:* The call ranker scores observed calls against the scanner's fresh scan artifacts (reports/scan/), not the committed tables.

*Reasoning:* The code in `load_scan` and `load_scans` functions explicitly loads scan artifacts from the `reports/scan/<server>.json`, not from `reports/samples` or `reports/evaluation`. The `score_corpus` function uses these loaded scans for scoring, ensuring that design-time tables are never used as inputs to scoring.

*Evidence:* src/mcp_security/call_scoring/tables.py: load_scan, load_scans; src/mcp_security/call_scoring/corpus.py: score_corpus

## ✅ no_unjustified_hardcoded_scores — pass (severity: none)

*Claim:* Risk magnitudes AND bands are LLM-derived: score_bands asks the model for each cell's band, and in strict mode (the scanner's mode) it _strict_fails rather than computing one. The only fixed logic is the documented score formula (sensitivity*blast*impact); band_label is a clearly-labelled OFFLINE/non-strict fallback, never used on a strict scan.

*Reasoning:* The code ensures that when `strict=True`, the `_strict_fail` method is called if the LLM does not provide a usable answer, preventing any hardcoded fallbacks from being used. The `band_label` function is only invoked in non-strict mode.

*Evidence:* _strict_fail method in src/mcp_security/static_scoring/pipeline.py and band_label function usage conditional on strict mode

## ✅ deterministic_scoring — pass (severity: none)

*Claim:* Scoring is reproducible: the model is queried greedily with a fixed seed.

*Reasoning:* The code specifies a fixed seed and zero temperature in the default options, ensuring reproducibility of model responses.

*Evidence:* src/mcp_security/llm/ollama_client.py: DEFAULT_OPTIONS = {"temperature": 0, "seed": 0, "top_p": 1.0}

## ✅ honest_unresolved_handling — pass (severity: none)

*Claim:* Calls that do not resolve to a scanned cell are reported as unresolved/invalid statuses, never given a fabricated score or band.

*Reasoning:* The code ensures that calls which do not resolve to a scanned cell are reported with an honest status (either 'invalid' or 'unresolved') and never given a fabricated score. The `score_call` function checks if the tool is present in the scan's tool set, and if not, it returns an 'invalid' status. If the asset cannot be resolved, it falls back to reporting an 'unresolved' status.

*Evidence:* src/mcp_security/call_scoring/score.py: ScoredCall._of, score_call function
