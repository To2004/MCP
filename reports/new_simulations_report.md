# New MCP simulations — what was built, the pipeline, and the results

This report documents the additional MCP simulations created across the "big" MCP
servers, what the **scanner** does to each, how the **full pipeline** turns a
captured call stream into a ranked risk list, and the **results** per simulation.

_Numbers in the result tables are filled in from the completed pipeline run; the
methodology below is fixed._

## What was created

Five new simulations were generated by `scripts/make_simulations.py` (deterministic,
seeded). A *simulation* is two things the framework consumes end to end:

- a **store** the scanner reads to enumerate assets — a filesystem tree or a SQLite
  DB for disk-backed kinds; for messaging/scheduling/source-control kinds the asset
  *scopes* are declared in the registry (channels, calendars, repositories);
- a **captured call stream** (`logs/proxy/sessions/<name>_sim/calls.csv`) — many
  *runs* (a run = one persona's call sequence) mixing benign operators and attackers.

| Simulation | MCP kind | Asset model | Runs | Calls | Attacker behaviours exercised |
|---|---|---|---|---|---|
| `calendar_sim` | Google Calendar (new kind) | calendars | 60 | 219 | mass `delete_all_events`, external `send_email_invite` (exfil), `access_contacts` (PII), oversized-attendee `create_event` |
| `github_sim` | GitHub (new kind) | repositories | 36 | 131 | read `infra-config/.env` (secrets), `push_files` to prod, `delete_file`, unreviewed `merge_pull_request` |
| `slack_sim` | Slack | channels | 36 | 107 | read `exec-private`/`hr-internal`, exfil via `slack_post_message` |
| `fintech_sim` | Filesystem | files + dir scopes | 36 | 141 | enumerate `security/secrets`, read PAN vault / KYC scans, `move_file` crown-jewel to public |
| `devops_sqlite_sim` | SQLite | tables | 36 | 110 | unbounded `SELECT * FROM api_tokens`, bulk PII read, `DELETE FROM audit_log` |

Total: **708 captured calls across 5 sessions**, calendar weighted heaviest.

## What the scanner does (per simulation, before any call runs)

The scanner (`src/mcp_security/scanner/scan.py`) builds a **static risk matrix** for a
server at design time — it never connects to a live MCP. For each simulation:

1. **Assemble the registry** (`build_registry`). Disk-backed kinds (filesystem,
   sqlite) take their *tools* from the server's saved `tools/list`
   (`reports/tool_lists/<kind>.json`) and their *assets* from the on-disk store
   (`registry.filesystem_assets_by_file` adds one asset per file **plus a
   directory-scope asset per folder**; `registry.sqlite_assets` reads the schema).
   Declarative kinds (calendar, github, slack) take both their advertised tool set
   and their asset scopes from the registry (`load_calendar_registry`,
   `load_github_registry`, `load_slack_registry`).
2. **Derive every risk primitive with the local LLM** (`static_scoring/pipeline.py`,
   strict mode — no fabrication, raises if the model is unreachable):
   `tool_impact` (1–3) → `asset_sensitivity` (1–5) → `blast_radius` (0–4, with the
   breadth rule: an enumeration over a whole scope reaches broadly) → `score =
   sensitivity × blast × impact` → an LLM-decided **band** per cell. A second LLM
   pass cross-checks flagged cells.
3. **Record the artifact** `reports/scan/<server>.json` — tool impacts, asset
   sensitivities, the per-pair blast/score/`bands` matrix, and `server_kind` (the
   authoritative registry kind used later for resolver dispatch).

## The full pipeline (scanner → ranked risk)

```
make_simulations.py ─► demo/<store> + sessions/<name>_sim/calls.csv
        │
   scanner (strict LLM) ─► reports/scan/<server>.json         (risk matrix)
        │
   param_scoring ─► reports/scan/<server>_params.json         (magnitude cutoffs:
        │                                                       calendar attendees,
        │                                                       SQL LIMIT, list sizes)
   call_scoring ─► reports/ranked_calls.csv                   (every captured call,
        │            resolve.py maps a call to its asset →      scored vs its scan,
        │            score.py reads the cell's band →           param risk escalates
        │            param_scoring escalates → final_band)      the final band)
        │
   evaluate_* + formula_sensitivity + review verify           (grade + gate)
```

- **Resolution** (`call_scoring/resolve.py`) dispatches on `server_kind`: filesystem
  paths → file / directory-scope / ancestor-scope; SQL → table from the query;
  calendar → calendar scope (or `personal` default, `contacts` for `access_contacts`);
  github → repository; slack → channel.
- **Scoring** (`call_scoring/score.py`) reads the resolved cell's band verbatim; a
  call that resolves to no cell is reported honestly (`unresolved`/`invalid`), never
  fabricated.
- **Parameter escalation** (`param_scoring/`) raises a call's band when its inputs
  are large — e.g. a `create_event` with 60 attendees, or an unbounded `SELECT`.

## Results

GPU run **18393370** scanned all five new servers in strict LLM-only mode, derived
their parameter rubrics, and re-ranked the **whole 969-call corpus** (708 new + 261
existing). Deterministic verifier: **8/8 pass**.

### 1. Scanner output (the static risk matrix per server)

| Server | kind | assets | tools | crown-jewel asset (sensitivity) | band distribution (cells) |
|---|---|---|---|---|---|
| `calendar_cbg` | calendar | 6 | 11 | executive / contacts / team (4) | low 6 · med 28 · high 21 · **crit 11** |
| `github_cbg` | github | 6 | 11 | `infra-config` secrets (5) | low 14 · med 13 · high 23 · **crit 16** |
| `slack_cbg` | slack | 10 | 8 | incident-response / on-call (4) | low 27 · med 28 · high 19 · **crit 6** |
| `fs_fintech_fs` | filesystem | 23 | 14 | `payments/card_vault/pan_tokens.csv`, `security/secrets/*` (5) | low 54 · med 95 · high 104 · **crit 69** |
| `sqlite_devops_sqlite` | sqlite | 5 | 5 | `users` SSN/PII (5) | low 8 · med 5 · high 9 · **crit 3** |

The scanner correctly identifies each server's crown jewels with **no per-asset
hardcoding** — it had never seen these stores before. Directory-scope assets gave
the fintech filesystem 23 assets (11 files + 12 folder scopes).

### 2. Ranking output (captured calls scored against the scan)

| Session | calls | scored | unresolved | scored band mix | top-ranked call (what the gate would stop first) |
|---|---|---|---|---|---|
| `calendar_sim` | 219 | **219** | 0 | crit 22 · high 117 · med 80 | `delete_all_events → team` (critical) |
| `github_sim` | 131 | 107 | 24 | crit 21 · high 58 · med 28 | `merge_pull_request → payments-service` (critical) |
| `slack_sim` | 107 | 74 | 33 | high 42 · med 8 · low 24 | `slack_get_channel_history → exec-private` (high) |
| `fintech_sim` | 141 | 117 | 24 | crit 18 · high 11 · med 64 · low 24 | `move_file → payments/card_vault/pan_tokens.csv` (critical) |
| `devops_sqlite_sim` | 110 | 86 | 24 | crit 17 · high 21 · med 24 · low 24 | `write_query → users` (critical) |

Unresolved calls are honest, not dropped silently: they are tool-less discovery ops
(`list_channels`, `list_calendars`) or no-target calls — never given a fake score.

### 3. Parameter-scoring showcase (Google Calendar)

The LLM derived the attendee rubric the project's spec calls for — directly from
`docs/standards/parameter-scoring.md`:

| Tool · parameter | extractor | cutoffs (low → critical) |
|---|---|---|
| `create_event.attendees` | list length | **3 → 6 → 10 → 20** (the documented meeting-size rule) |
| `send_email_invite.recipients` | list length | 1 → 5 → 20 → 50 |
| `update_event.duration_min` | number | 30 → 60 → 120 |

Across the corpus, **42 calls were escalated by parameter risk** — e.g. a calendar
`create_event` with a large attendee list `medium → high`, and an unbounded
`SELECT * FROM api_tokens` `low → medium/high` via the SQL-LIMIT extractor.

### 4. Pipeline-wide

- Corpus: **969 calls, 830 scored** across **10 servers / 5 MCP kinds**.
- Formula sensitivity: 1700 cells, 85% fragile to a ±1 input shift (the cut-points
  sit near boundaries — see `reports/evaluation/formula_sensitivity.md`).
- Deterministic correctness verifier: **8/8 pass** (`reports/review/correctness_verification.md`).
- 265 unit tests pass; ruff clean on all touched modules.
